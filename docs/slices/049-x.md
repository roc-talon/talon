# 049 tln x and build reuse

Phase: P1. Status: done

Slice 049 adds `tln x owner/app [-- args]` (CLI 6.4: R-CM12, R-X1 to R-X5), the `x` cache and the reuse of builds (R-B1 to R-B5, R-B7 to R-B10, R-NI9), and the GC rule for `x` entries (R-GC7, from the review of slice 028). Slice 046 made `tool install`, slice 047 made the compiler choice, slice 048 made `tool ls`, `rm`, `update`, `rebuild` and `--git`. Now `tln x` builds an app into the `x` cache and runs it. `tool install` takes a matching entry from the cache in place of a build.

Size (TW19): the plan row says 400 lines. The private reference has 993 lines in 5 new modules (`XCache` 356, `XCmd` 118, `XCacheIo` 106, `XTake` 198, `XFlow` 227), and 47 more lines in `ToolFlow.roc`, 10 in `ToolBuild.roc`, 5 in `CacheGc.roc`, 3 in `Run.roc` and 5 in `main.roc`. About 40 percent of the lines are doc comments (tables of the calls and of the rules). A split is proposed in section 12.

Live reads: none. No real network and no real long build in L0 to L3. L3 uses a fake compiler (a shell script), the real `curl`, the real `roc unbundle` and the real `exec`.

## 6. Decisions that the design does not fix (the test agent chose, for review)

| # | Decision | Options rejected |
| --- | --- | --- |
| D1 | The digest has the bundle hash, so two releases with the same dependencies and compiler have two dirs (R-B9 puts the bundle hash in the manifest, R-X2 names the build id) | The build id alone (a collision: `1.0.0` and `1.1.0` with the same dependencies) |
| D2 | The file in an entry is the repo name (`.exe` on Windows), not the binary name of a tool (`--as` is for tools only) | The key of the tool |
| D3 | `x` writes the manifest again with `last_run` at each run (the first build sets it to the build time). R-GC7 needs the time of the last run | A file mtime (a copy, a backup or a touch changes it) |
| D4 | The order of a take-over: sha256 check of the cache binary, `rename` (or copy) to the data bin dir, the bin dir entry, `tools.json`, then delete the entry dir. The check is before the move: a changed file never replaces an installed binary | Check after the move (the installed binary is already lost) |
| D5 | R-B3 online, read literally: only the winner (the highest version) is checked against the release list. When it is no candidate, no other build is tried and the newest release is built | Try the next build (R-B3 does not say) |
| D6 | The case "no network" is any failure of the kind `Network` of the release list (this also covers a rate limit and a status failure). Then the offline path runs, with no cached index (the index path of `tool install --offline` stays for no match) | Only a transport error |
| D7 | `x --git`, `--path` and `--resolve` give `is not built yet` (as slice 046). Git `x` entries and the take-over of a git build are for a later slice | Build the git source here |
| D8 | GC reports `x` entries inside `builds` (the report line and `data.builds`), no new `Done` field | A new field `x` (churn in `GcTest` and in all gc JSON expected files) |
| D9 | Offline, only no selector or an exact version matches a build (Q-O2) | `latest` and ranges match the highest cached build |
| D10 | An entry with a newer `format` or content that does not parse is handled as R-TF3 and R-TF6 say: the first is ignored (also by GC), the second is deleted with a warning | Delete both |
| D12 | (review, Q-X3) An entry is a match only when its dir has a file besides `manifest.json` (`Found.has_bin`, one `list_dirs!` of the entry dirs in `XCacheIo.entries!`). The build that replaces it gets the old dir in `stale`: `XCacheIo.write!` deletes that dir before the `rename` | A check with `sha256_file!` at each run (a full read) |
| D11 | The offline prompt of a take-over says `Install it?` and the one of `x` says `Run it?`. Both use the id `use-unchecked` | One text |
